# NMO Seva Ledger — iOS

This folder contains the SwiftUI iOS companion app for the same NMO collector backend used by Android.

## What the iOS app supports

- Same collector code + token model as Android
- Same Google Apps Script `/exec` backend
- Same central `Ledger` sheet and collector-wise admin dashboard
- Dark NMO-styled SwiftUI interface
- Incoming transaction review: Donation / Personal / Decide later
- Outgoing transaction review: Campaign expense + comment / Personal / Decide later
- Local offline ledger on the iPhone
- Manual transaction entry
- Share Extension that can parse explicitly shared payment-confirmation text and place it into the local ledger for review
- Sync of pending changes to the same backend event schema used by Android

## Important iOS limitation

iOS does not provide a general equivalent of Android `NotificationListenerService`. NMO Seva Ledger therefore cannot automatically read PhonePe, Google Pay, Paytm, BHIM or WhatsApp notifications generated by those other apps.

The closest supported workflow is:

1. Use the payment app's Share option when it exposes payment-confirmation text, then choose **NMO Seva Ledger** in the iOS share sheet; or
2. Use **Add transaction** inside NMO Seva Ledger.

Shared text is parsed only when it contains a currency amount and payment-like wording. Ordinary shared chat text is ignored when it cannot be identified as a payment.

## Build on a Mac

The iOS app must be built with Xcode on macOS.

This repository uses `project.yml` so the Xcode project can be generated with XcodeGen.

```bash
brew install xcodegen
cd ios
xcodegen generate
open NMOSevaLedger.xcodeproj
```

Then in Xcode:

1. Select the **NMOSevaLedger** target → **Signing & Capabilities**.
2. Choose your Apple Developer team.
3. Enable **App Groups** for both `NMOSevaLedger` and `NMOShareExtension`.
4. Use the group identifier `group.org.nmo.seva.ledger` for both targets.
5. If your Apple Developer account requires a unique bundle ID, change `org.nmo.seva.ledger` and the share-extension bundle ID in `project.yml`, and use the matching App Group identifier in both entitlement files and the Swift source.
6. Run on a real iPhone.

## Collector setup

Use the same Apps Script deployment already used by the Android collectors.

Each iPhone collector enters:

- Collector name
- Unique collector code such as `NMO02`
- Their own collector token generated by `addCollector(...)`
- Existing Apps Script `/exec` URL

Do not generate a new token merely because a collector changed from Android to iPhone. A new token is needed only for a new collector identity or deliberate credential rotation.

## Share import

The `NMOShareExtension` writes parsed payment metadata into the shared App Group container. The main app consumes those pending imports on launch and inserts them into the local ledger as `PENDING` review items.

Examples the first parser version is intended to recognize include payment-like text containing:

- `You received ₹500 ...`
- `Received Rs.500 ...`
- `You sent ₹500 ...`
- `You paid Rs.500 ...`
- wording containing `credited`, `debited`, `paid to`, `sent to`, `sent you`, or `to you`

Because share text differs across payment apps and versions, real payment-share text should be tested before campaign use.

## Accounting reliability

Like the Android notification approach, the iOS share/manual workflow is an operational ledger aid, not bank settlement verification. Final campaign accounting should be reconciled with the relevant UPI/bank transaction history.
